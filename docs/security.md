# Обеспечение безопасности приложения

УП.02, вариант 5, работа 28.

Безопасность построена на трёх уровнях: защищённый канал (HTTPS), аутентификация и роли (JWT) и правильное хранение секретов. Проверки выполнялись и модульными тестами, и живым API на чистой SQLite (`tools/smoke_live_api.py`, **26/26**), и UI-тестами (**8/8**).

## 1. Чек-лист безопасности

| Механизм | Реализация | Подтверждение |
|---|---|---|
| Защищённый канал | Только HTTPS; отдельный API — `https://localhost:7130`, WPF поднимает API на loopback | Живые проверки через HTTPS, 26/26 |
| Самоподписанный сертификат | `LoopbackCertificate.Create()` создаёт RSA-2048 / SHA-256 сертификат `CN=DeliveryService.Local` с SAN `127.0.0.1`, сроком действия 2 дня; PFX очищается из памяти | Клиент подключается без установки корневого сертификата |
| Pinning сертификата | `DeliveryService.Desktop/App.xaml.cs:31–42` сверяет `GetCertHash(SHA256)` с ожидаемым через `CryptographicOperations.FixedTimeEquals` | Подмена сертификата отвергается |
| JWT Bearer | `SessionTokens.Issue`: HMAC-SHA256, 8 ч, `iss=DeliveryService`, `aud=DeliveryService.Client`, claims `sub/jti/login/display_name/role` | Выдачу и проверку токена покрывают тесты |
| Отзыв токена | `SessionTokens.Revoke` помечает `jti` в `IMemoryCache` до момента `exp`; `POST /api/auth/logout` доступен всем ролям | Повторное использование токена после выхода невозможно |
| Object-level права | Курьер видит только свои отправления; чужой объект — 404; роли Admin/Operator/Courier проверяются на сервере | 26 проверок живого API, включая ограничения на уровне объекта |
| Хранение паролей | `Pbkdf2PasswordHasher`: PBKDF2-SHA256, **100 000** итераций, **16-байтовая** соль, 32-байтный ключ, сравнение через `FixedTimeEquals` | Пароли в БД отсутствуют в открытом виде; демо-пароли вымышленные |
| Ограничение входа | Fixed-window rate limiter `Security:LoginAttemptsPerMinute` = **5 попыток/мин** на IP, диапазон 1–1000 (`DeliveryHost.cs:44–45,117–125`) | Проверка 429 и разблокировки в тестах |
| Секреты в репозитории | Отсутствуют; ключ JWT задаётся через User Secrets | Проверка репозитория: только вымышленные демо-данные |
| Журналирование | Serilog, ротация по дням, хранение 14 дней; ошибки входа и denied-доступ фиксируются | См. [failures.md](failures.md), раздел о журналах |

## 2. Команды настройки

```bash
# Ключ JWT (не менее 32 символов) — только в User Secrets, не в файлах проекта
dotnet user-secrets set "Jwt:Key" "<>=32 chars>" --project DeliveryService.Api

# Доверие dev-сертификату нужно только для отдельного запуска API
dotnet dev-certs https --trust
```

Для WPF-клиента доверие **не требуется**: он сам запускает API и проверяет сертификат по SHA-256. Для отдельного запуска API команда `--trust` обязательна.

Архив `artifacts/DeliveryService-1.0.0-win-x64.zip` собран офлайн-восстановлением с `NuGetAudit=false`. Ранее выполненный онлайн-аудит и его результаты остаются действительными, но перепроверка в момент сборки ZIP не проводилась.

## 4. Итог

Канал, токены, роли, хранение паролей, ограничение частоты входов и работа с секретами соответствуют требованиям NFR и методичке. Единственное задокументированное ограничение — недоступность `nuget.org` при финальной упаковке; оно не влияет на работу приложения, но должно учитываться при повторной сборке в сети.
