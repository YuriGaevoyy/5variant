# Измерение производительности до и после оптимизации

УП.02, вариант 5, работа 26.

Измерения проведены на наборе из **10 000 записей** в проекте `tools/DeliveryService.Benchmarks` (консольный драйвер измерений на `Stopwatch`), сборка **.NET 10 Release**. Результаты воспроизводимы: генератор использует фиксированное значение `Random(2026)`, статусы и даты распределены равномерно, все суммы — `decimal`.

## 1. Методика

| Параметр | Значение |
|---|---|
| Объём выборки | 10 000 отправлений (`const int rows = 10_000`) |
| Итераций | 12 для статистики, 3 для экспорта (медиана) |
| Разогрев | 2 прогревочных вызова перед замером |
| Платформа | .NET 10 Release, SDK 10.0.402 |
| Операции | Статистика (`NaiveStatistics` ↔ `ShipmentRules.StatisticsFromMetrics`); экспорт CSV (`NaiveCsv` ↔ `Exchange.ExportCsv`) |
| Статистика | Медиана отсортированных измерений, `Stopwatch.Elapsed.TotalMilliseconds` |
| Воспроизводимость | `tools/DeliveryService.Benchmarks/Program.cs`, сид 2026 |

Медиана выбрана сознательно: она устойчива к случайным паузам планировщика и сборщику мусора. Для экспорта числа и даты форматируются через `CultureInfo.InvariantCulture`, чтобы сравнение не зависело от региональных настроек.

## 3. Причина ускорения

**Статистика.** «До» — `NaiveStatistics`: для каждого статуса выполнялся отдельный проход `rows.Where(...).Count()`, затем ещё проходы для сумм, доставленных и длительностей. Итого до десятков проходов по коллекции и множеству временных перечислений. «После» — `ShipmentRules.StatisticsFromMetrics` (`DeliveryService.Core/ShipmentRules.cs:65`): один проход `foreach`, массивы счётчиков по статусам, накопление `decimal`-сумм и средней длительности. Результат — 4,70×.

**Экспорт.** «До» — `NaiveCsv`: `csv += ...` в цикле, то есть многократное копирование уже накопленной строки (квадратичная сложность по объёму вывода). «После» — `Exchange.ExportCsv` (`DeliveryService.Core/Exchange.cs:85`): один `StringBuilder` с заранее известной ёмкостью и `Append`/`AppendLine`. Результат — 88,53×. Экспорт JSON и XML использует тот же отформатированный набор данных, поэтому расхождения в идентификаторах, статусах и метках времени исключены.

## 5. Вывод

Цель методички — уложить выборку 10 000 записей в 1 с (НФТ-04) — достигнута с большим запасом: экспорт занимает 12,79 мс вместо 1131,95 мс, статистика — 0,19 мс вместо 0,87 мс. Оптимизация не изменила бизнес-правила: те же 64 теста и 26 проверок живого API проходят после правок; покрытие `Core` остаётся 238/251 = 94,8 %.
