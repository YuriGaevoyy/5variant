# Тест-кейсы службы доставки

УП.02, вариант 5, работы 3 и 4.

Проверки выполняются на временной SQLite с демоданными: не менее семи отправлений в разных статусах, два курьера с разными назначениями и четыре учётные записи. Статус «Пройдено» означает, что поведение зафиксировано в модульных, интеграционных или UI-тестах. Идентификаторы требований совпадают с [requirements.md](requirements.md), поэтому столбец «Требование» служит матрицей трассировки.

## Приёмочные сценарии

1. **Дано** оператор вошёл и выбрал получателя. **Когда** он создаёт отправление и назначает курьера. **Тогда** карточка начинается со статуса «Создано» и доступна курьеру; переход «В пути» без назначения отклоняется. Проверки TC-05 и TC-07.
2. **Дано** отправление «В пути». **Когда** курьер указывает сумму, ФИО получателя и время доставки. **Тогда** статус меняется на «Доставлено», время хранится в UTC. Проверка TC-11.
3. **Дано** CSV с одной корректной и двумя ошибочными строками. **Когда** оператор загружает файл. **Тогда** API возвращает 400 с номерами строк и не сохраняет записи. Проверка TC-16.
4. **Дано** в систему вошёл `courier1`. **Когда** он запрашивает карточку отправления `courier2`. **Тогда** сервер возвращает 404. Проверка TC-14.

Список HTTP-проверок с ожидаемыми кодами приведён в [api-tests.md](api-tests.md), а оформление интерфейса — в [ui-checklist.md](ui-checklist.md).
